# Runbook

Routine tasks and first responses. Local commands assume the repo root.

## Daily

| Task | Command |
|---|---|
| Start the stack | `docker compose up -d` |
| Stop it | `docker compose down` |
| Stop it and wipe the database | `docker compose down -v` — destroys `postgres-data` |
| Backend logs | `docker compose logs -f backend` |
| Rebuild after `requirements.txt` | `docker compose up -d --build backend` |
| Inspect the database | Adminer at <http://localhost:8080>, server `postgres` |
| API docs | <http://localhost:9000/docs> |

## Diagnosis

### The backend will not start

Check the logs first: `docker compose logs backend`.

| Symptom | Cause |
|---|---|
| `ValidationError` naming `s3_bucket_name` or `s3_region` | Both are required and have no defaults. Set them in `.env`. |
| Alembic error at startup | A migration failed; the app aborts rather than serving a stale schema. The traceback names the revision. |
| Cannot reach Postgres | The backend waits for the healthcheck. `docker compose ps` — is postgres `healthy`? |

### Uploads return 500, everything else works

Almost always missing `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`. boto3 cannot sign
without them. No other feature depends on AWS.

### The frontend cannot reach the API

Running the frontend on the host, it uses `BACKEND_URL`, defaulting to
`http://localhost:9000`. Inside Docker it must be `http://backend:9000` — `localhost` there
means the container itself.

Check the API is actually up: `curl -s -o /dev/null -w '%{http_code}' http://localhost:9000/docs`.

### Everyone is logged out at once

`JWT_SECRET_KEY` changed. Every existing token fails signature verification. Restore the
previous value if this was unintentional.

### A user cannot log in

In order: is the account `is_active`? (A disabled account returns a distinct message.) Is
the password right — there is no reset flow, so the only remedy today is updating
`password_hash` directly. Has their refresh token been revoked by a sign-out elsewhere?

## Database

```bash
# shell
docker compose exec postgres psql -U postgres -d lumen

# backup
docker compose exec -T postgres pg_dump -U postgres lumen > backup.sql

# restore
docker compose exec -T postgres psql -U postgres -d lumen < backup.sql
```

The `postgres-data` volume is the only copy of everything. **No backups are scheduled.**

### Useful queries

```sql
-- active sessions for a user
SELECT jti, created_at, expires_at, revoked_at
FROM refresh_tokens WHERE user_id = $1 ORDER BY created_at DESC;

-- revoke every session for a user (forces re-login everywhere)
UPDATE refresh_tokens SET revoked_at = now()
WHERE user_id = $1 AND revoked_at IS NULL;

-- disable an account
UPDATE users SET is_active = false WHERE email = $1;

-- snapshot growth, largest files first
SELECT fe.name, count(*) AS versions, pg_size_pretty(sum(length(fs.content))::bigint) AS total
FROM file_snapshots fs JOIN file_entries fe ON fe.id = fs.file_id
GROUP BY fe.id, fe.name ORDER BY sum(length(fs.content)) DESC LIMIT 20;
```

That last one matters: snapshots store whole content per version and are never pruned, so
this is the table that will grow without bound.

## Migrations

```bash
cd backend
.venv/bin/python -m alembic revision --autogenerate -m "describe the change"
.venv/bin/python -m alembic upgrade head     # or just restart the app
.venv/bin/python -m alembic downgrade -1
```

Review autogenerated revisions before committing — Alembic misses column renames, seeing a
drop plus an add, which loses data.

## Tests

```bash
cd backend  && .venv/bin/python -m pytest
cd frontend && bun run test
cd frontend && bun run test:e2e:local    # no backend needed
```

Nothing runs these automatically yet.

## Monitoring

Sentry, when `SENTRY_DSN` is set; disabled otherwise. There is no uptime monitoring, no
alerting, and no metrics.
